# AI 驱动的 HYSYS 反应器智能建模项目报告

提交人：________　　日期：2026 年 10 月 4 日

## 项目目标与完成情况

这次项目，我想做的是让用户用自然语言描述反应过程，系统就能判断合适的反应器，在 Aspen HYSYS 中建立案例，并把计算结果和选型理由一起返回。按照考核要求，我完成了甲苯歧化、甲烷蒸汽重整和水煤浆气化三个场景的建模链路。工作站上的运行输出显示，三个场景均已完成真实 HYSYS 计算；其中气化曾在生成报告时出错，计算结果已经保存，后来通过恢复脚本成功生成了报告。

目前，系统提供中文 Streamlit 聊天界面，支持自然语言输入、信息追问、多工况计算和报告下载。页面也会显示模型抽取、选型预检、用户确认、HYSYS 执行和报告生成的实际过程，便于录屏时说明每一步做了什么。新界面的过程展示已通过离线测试，最终提交前还需要在工作站上录制完整演示。

## 技术选型与系统架构

我选择 Python 3.12 作为主要语言，通过 pywin32 调用 HYSYS 的 COM 接口。这样可以直接配置物流和反应器、读取结果并保存案例，比依赖窗口位置和鼠标点击更适合重复测试。前端采用 Streamlit，是因为它能较快实现聊天和结果展示，同时复用原有 Python 业务逻辑。

系统分为智能体层和工具层。智能体层先用在线模型抽取组分、流量、温压、反应式等事实，再进行一次独立模型审核，对照原文修正遗漏并记录依据；随后由 Python 完成名称归一化、单位换算、反应器选型、规格编译和预检。工具层接收严格的 JSON 规格，驱动 HYSYS 求解，再独立检查守恒关系和相关计算指标。模型不直接执行 COM 命令，也不负责生成最终模拟数值。

流程使用 LangGraph 编排，通过检查点保存任务状态。遇到缺失或有歧义的信息，系统暂停并追问，用户回答后继续原任务。数据结构通过契约约束和类型校验控制，避免模型输出一个“看起来合理”的对象就直接进入模拟。模型接口采用兼容 `/chat/completions` 的协议，页面可设置服务地址、模型名称和密钥；当前实测使用 qwen3.7-flash。

## 三个场景的选型与真机结果

| 场景 | 选型依据 | 工作站运行结果 |
| --- | --- | --- |
| 甲苯歧化 | 已知甲苯转化率为 50%，不研究动力学，采用 Conversion | 绝热出口温度 378.28°C；摩尔组成为甲苯 50%、苯 25%、三种二甲苯各约 8.33% |
| 甲烷蒸汽重整 | 两个可逆反应构成闭合网络，无动力学参数，采用等温 Equilibrium | 710°C 与 600°C 下，甲烷转化率分别为 54.16% 和 30.50%；出口 Q/K 均接近 1 |
| 水煤浆气化 | 高温、多种候选产物、需要考虑副反应，采用 Gibbs 加饱和碳路线 | 1400°C 下 CO 收率为 40.14%，碳转化率为 41.16%；湿基气相 CO 摩尔分数约 50.01% |

以上数值取自工作站返回的运行记录。甲苯案例中，题目没有给出三种二甲苯的比例和热边界，我按等摩尔分配及绝热处理，并在报告中明确标注。气化案例则先确认标准体积的解释和煤按纯碳处理的假设，再进行计算。题目没有给氧气进料，因此报告中的热负荷代表维持出口温度所需的外部供热。

为检查系统能否处理变化后的输入，我还测试了甲烷 1000 kmol/h、水蒸气 3000 kmol/h、压力 10 bar、出口温度 650°C 和 750°C 的重整工况。两种温度下甲烷转化率分别为 47.78% 和 73.99%，氢气流量分别约为 1776.78 和 2583.07 kmol/h，外部供热负荷分别约为 34.09 和 55.98 MW。该次运行先经过总流量确认，然后完成模拟；结果呈现了升温后重整程度增加的趋势。

## 探索过程与问题处理

开发过程中，我逐渐把模型的职责收敛到信息抽取，把工程判断交给可测试的规则代码。模型即使遵循提示词，也可能合并组分名称或给出不合适的反应系数，因此下游必须检查反应配平、字段类型和输入依据。提示词中的完整 JSON 示例采用乙醇脱水，与三个考核场景不同，用来说明数据格式；提示词仍包含二甲苯拆分等领域规则，不能据此声称系统已经适用于所有反应体系。

一个比较典型的问题出在校验器本身：重整没有指定转化率，模型返回 `conversion_basis: null` 是合理的，但原来的 schema 只允许字符串，导致正确回复被连续拒绝。我放宽了允许缺失的文本字段，保留对象和数组的严格类型约束，并加入回归测试。存档的四份回复重新校验后全部通过，重跑重整也恢复为一次模型请求即可完成正常抽取。

甲苯测试还暴露了二甲苯异构体展开后系数不正确的问题，导致元素守恒预检失败。修复后，三种异构体按总系数的三分之一分配，真机运行通过。气化的另一处故障发生在报告层：代码把字符串当成字典读取，计算已经成功却无法展示。我增加了结果结构兼容处理，并通过保存的产物恢复报告，避免重新调用模型或重复运行 HYSYS。

这些问题让我更重视“失败发生在哪一层”。模型抽取错误、规格校验错误、HYSYS 求解失败和报告生成失败，处理方式并不相同。现在页面会保留对应阶段和状态，报告也区分用户给定、系统假设和计算推导，方便复查。

## 验证边界与后续交付

接入输入审核、修正多工况压力并完善审核追问后，智能体层 499 项回归测试通过。真实审核记录也暴露了一个问题：审核模型会把推理当成原文引用，导致条件完整的题目仍被追问。我增加了原文明确条件的确定性检查，并保存这份审核记录作离线回归。对于审核回复格式不合法的情况，也补上了具体字段诊断和预算内一次格式修复，失败时保存回复供排查。提交打包相关测试共有 17 项；工具层已有 122 项自检、184 项回归测试和真机验收记录。离线测试用于检查流程、追问、数据处理和界面行为，不能代替工作站上的真实求解，新增审核流程也需要继续做实际模型验证。

系统当前主要覆盖已验收的三类建模路径，CSTR 和 PFR 尚未实现。重整的 Q/K 校验说明结果与使用的平衡常数一致，但不能证明 HYSYS 高温 Gibbs 数据本身准确；煤按纯碳处理也是简化假设，需要在解释气化结果时保留。

AI 编程助手参与了方案讨论、代码实现、缺陷排查和测试补充。我通过工作站实际运行、保存产物和复核结果来检查这些修改，而不是仅凭生成的解释判断是否成功。接下来，我会用最新界面录制三个场景从输入到结果的完整过程，整理 AI 开发记录，并按提交版本复查安装说明和演示步骤，完成最后的交付。
