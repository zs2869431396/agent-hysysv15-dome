# AI 驱动 HYSYS 建模项目：数据流详解

本文按一次请求从自然语言到中文报告的顺序，解释每一步的输入、输出、放行条件和失败去向。依据是当前仓库代码；示例数值以仓库内的工具层真机验收结果为准。

可视化版本：[打开独立 HTML 流程图](项目完整流程图.html)。

## 1. 总览

```text
自然语言输入（Streamlit / CLI）
  ↓
LLM 抽取结构化事实
  ↓
程序做基础字段校验和原文溯源，标记无依据的值
  ↓
review 节点：程序先补回原文明示的信息，并试规划、预检以定位缺口
  ├─ 没有可补漏的目标字段：跳过第二次 LLM 调用
  └─ 有目标字段：LLM 只核对指定字段并引用原文
       → 程序验收候选修正 → 再次预检
  ↓
plan 节点：归一化 → 反应器选型 → 能力检查 → 编译 JSON 规格 → 最终预检
  ├─ 有阻塞问题：LangGraph 暂停 → 用户回答 → 从检查点重新规划
  ├─ 不支持或预检失败：明确停止并给出原因
  └─ READY：方案模式只输出规格；执行模式进入工具层
       ↓
适配器逐工况启动 hysys_tools 子进程
       ↓
HYSYS COM 建案例 → 配置 → 求解 → 读回 → 独立校验 → 保存
       ↓
程序生成中文解释、工况对比和过程记录
```

**职责边界**：大模型理解用户原文；确定性 Python 代码负责选型、追问、编译和执行门控；HYSYS 负责模拟求解。未进入执行模式时，系统只能说“模拟方案已就绪”，不能说“模拟计算已完成”。

## 2. 用户入口：收到的是文字，不是模拟规格

用户可以在 `reactor_agent/streamlit_app.py` 的中文聊天界面输入，也可以从 `reactor_agent/__main__.py` 的 CLI 提交。界面提供“生成模拟方案”和“执行 HYSYS 模拟”两种模式。

**代码定位**：[Streamlit 输入框与提交，第 162、174 行](../reactor_agent/streamlit_app.py#L162)；[CLI `main` 入口，第 370 行](../reactor_agent/__main__.py#L370)；[图初始状态，第 67 行](../reactor_agent/nodes/state.py#L67)；[主图节点连接，第 64–89 行](../reactor_agent/graph.py#L64)。

例如用户输入：

> 甲烷和水蒸气摩尔比 1:2.7，进料 520°C、13.5 bar；考虑蒸汽重整和水煤气变换，分别计算出口 600°C 和 710°C。

此时系统尚不能向 HYSYS 下命令。还需要确定组分、反应系数、进料规模、两个独立工况、热边界及所需反应器，并确认每项条件是用户给定还是系统假设。

## 3. LLM 抽取：自然语言变成结构化事实

`reactor_agent/nodes/intake.py` 调用 `extraction.py`，由模型抽取组分、进料量与单位、温压、反应式、转化率、动力学信息和操作工况。以上面的重整输入为例，抽取的事实应包括：

| 字段 | 抽取内容 |
| --- | --- |
| 进料 | CH₄ 与 H₂O，摩尔比 1:2.7 |
| 入口条件 | 520°C、13.5 bar |
| 反应 | CH₄ + H₂O ⇌ CO + 3H₂；CO + H₂O ⇌ CO₂ + H₂ |
| 出口工况 | 600°C 与 710°C |
| 动力学与指定转化率 | 未提供 |

这一阶段只整理事实。模型不能直接决定 HYSYS 的最终计算值；题目未提供的字段可以为空，不能为了填满 JSON 编造数据。抽取结果保存在图状态的 `facts` 中。

**代码定位**：[抽取节点调用 `extract_verified`，第 20–35 行](../reactor_agent/nodes/intake.py#L20)；[抽取与校验入口，第 887、956 行](../reactor_agent/extraction.py#L887)；[图状态 `facts` 字段，第 27 行](../reactor_agent/nodes/state.py#L27)。

## 4. 原文溯源：防止格式正确但内容错误

`extraction.py` 会核对模型输出的数据类型、数值、单位和物理量是否与原文对应。检查关注的问题包括：

- `13.5 bar` 是否被识别为压力，而不是流量或温度；
- `710°C` 是否属于出口工况，而不是入口条件；
- 模型给出的数值能否在用户原文找到依据；
- 组成、反应和单位是否有足够信息供下游解释。

例如原文是 `10000 kg/h`，模型却输出 `12345 kg/h`，JSON 即使合法，该数值也不能直接进入模拟。未获原文支持的字段会被标记并阻塞，直到程序找到有效依据或用户给出可解析的确认。

**代码定位**：[模型字段结构校验，第 273 行](../reactor_agent/extraction.py#L273)；[数值、单位和物理量溯源，第 592 行](../reactor_agent/extraction.py#L592)；[反应式溯源，第 761 行](../reactor_agent/extraction.py#L761)；[未获依据的字段进入图状态，第 24 行](../reactor_agent/nodes/intake.py#L24)。

## 5. 程序预检与定向补漏：区分“漏提”与“真缺失”

`reactor_agent/input_recovery.py` 先从原文直接恢复可唯一确定的单位或进料组成基准，再用已有规划和预检规则寻找具体缺口。只有产生可补漏的目标字段时，才第二次调用模型。随后分两种处理：

1. **原文已给，模型漏提**：例如文本写了 `13.5 bar`，抽取结果却没有压力。系统仅把压力及关联单位列为目标字段，再让模型回原文定向查找。候选修正必须有连续原文引用，并再次接受类型与溯源检查。
2. **原文本身不明确**：例如气化题的 `80000 Nm³/h` 未说明对应哪股进料、标准状态为何。这不是模型能从原文找回的事实，需要用户确认。

补漏模型不能改动白名单以外的字段、清空已有事实或缩减已有组分。它自己生成的问题只保留作诊断记录；最终是否追问由程序预检决定。输入完整时，这个阶段通常跳过第二次模型调用。

**代码定位**：[从预检产生目标字段，第 86 行](../reactor_agent/input_recovery.py#L86)；[执行定向补漏，第 114 行](../reactor_agent/input_recovery.py#L114)；[候选修正的字段、引用与清空限制，第 140 行](../reactor_agent/input_recovery.py#L140)；[图中 `review` 节点，第 122 行](../reactor_agent/review.py#L122)。

## 6. 归一化、选型和能力检查：事实变成工程方案

`normalize.py` 把别名、单位、组成基准和反应式转成统一内部表示，生成 `ProcessRequest`。随后 `selection.py` 按事实选择反应器。主要规则是：

| 条件 | 工程选型 |
| --- | --- |
| 有完整动力学与明确相态 | 按规则建议 CSTR 或 PFR；当前工具层尚不支持执行 |
| 已知转化率、无动力学 | Conversion |
| 可逆且有平衡数据，或反应网络闭合且出口温度明确 | Equilibrium |
| 高温、多候选产物、反应网络难以完整列出 | Gibbs 路线 |
| 信息不足 | 追问或报告不支持 |

重整例子中，两条反应覆盖列出的组分，未给动力学和转化率，两个出口温度明确，因此选择等温气相 Equilibrium。Gibbs 保留为对照。

`capabilities.py` 再按反应器、热边界、相态、反应数量和固体参与情况判断：

- `verified`：对应组合有真机验收，且当前工具层文件哈希仍与验收记录一致；
- `experimental`：存在代码路径，但没有对应真机验收；
- `unsupported`：当前不执行。

“工程上应选什么”与“工具目前能否执行”分开记录。若规则认为应选 PFR，系统会报告 PFR 尚未实现，不会暗中换成 Conversion。

**代码定位**：[归一化入口，第 640 行](../reactor_agent/normalize.py#L640)；[闭合反应网络判断，第 176 行](../reactor_agent/selection.py#L176)；[选型规则入口，第 363 行](../reactor_agent/selection.py#L363)；[能力组合判断，第 166 行](../reactor_agent/capabilities.py#L166)；[验收哈希核对，第 80 行](../reactor_agent/capabilities.py#L80)；[图中规划节点，第 78 行](../reactor_agent/nodes/plan.py#L78)。

## 7. 编译和离线规格预检：方案变成机器可执行的 JSON

`compiler.py` 把 `ModelingPlan` 编译为每个工况一份 `hysys-agent/spec/1` JSON。以下是 710°C 重整工况的核心结构，省略报告性字段：

```json
{
  "schema": "hysys-agent/spec/1",
  "fluid_package": {
    "property_package": "PengRob",
    "components": ["Methane", "Water", "CO", "Hydrogen", "CO2"]
  },
  "feeds": [{
    "basis": "molar_flow",
    "flows": {"Methane": 1000, "Water": 2700},
    "temperature": 520,
    "temperature_unit": "C",
    "pressure": 13.5,
    "pressure_unit": "bar"
  }],
  "reactor": {
    "kind": "equilibrium",
    "thermal_mode": "isothermal",
    "outlet_temperature": 710,
    "outlet_temperature_unit": "C"
  }
}
```

题目允许自定进料规模，因此 `1000/2700 kmol/h` 是示例设计基准，必须在假设中注明，并非用户原文给定。600°C 工况会单独编译为另一份规格。

编译器调用 `hysys_tools/precheck.py` 做不启动 HYSYS 的规格预检，例如检查组件是否齐全、反应是否元素守恒、单位是否有效、工况及反应器组合是否受支持。预检不通过时不创建案例。

**代码定位**：[单工况规格生成，第 329 行](../reactor_agent/compiler.py#L329)；[多工况编译、阻塞与预检，第 411 行](../reactor_agent/compiler.py#L411)；[工具层规格预检入口，第 50 行](../hysys_tools/precheck.py#L50)；[规划节点再检查每份规格，第 151 行](../reactor_agent/nodes/plan.py#L151)。

## 8. 阻塞问题、暂停和恢复

若关键信息仍缺失，计划状态为 `WAITING_INPUT`。`graph.py` 将流程路由到 `nodes/ask.py`，用 LangGraph `interrupt` 暂停；SQLite 检查点保留可序列化的图状态。

气化是典型例子：必须确认 `80000 Nm³/h` 的进料范围与标准状态，以及煤是否可按纯碳处理。界面可显示默认建议，但默认值只有在用户确认后才写入事实与规格。无效回答不会解除阻塞。回答后从检查点回到规划步骤，不重新抽取整个题目。

此时还没有进入 `execute` 节点，因而不会提前生成 HYSYS 案例。若选型不受支持或编译失败，系统明确结束并给出原因；不会带着未解决问题继续求解。

**代码定位**：[收集阻塞问题并确定状态，第 134–160 行](../reactor_agent/nodes/plan.py#L134)；[`interrupt` 暂停与答案处理，第 33 行](../reactor_agent/nodes/ask.py#L33)；[暂停后路由，第 69 行](../reactor_agent/nodes/ask.py#L69)；[SQLite 检查点入口，第 94 行](../reactor_agent/graph.py#L94)；[仅 `READY` 执行，第 35 行](../reactor_agent/nodes/execute.py#L35)。

## 9. 执行适配器：逐工况、串行、留证据

状态为 `READY` 且用户选择执行模式时，`nodes/execute.py` 调用 `adapters/hysys_cli.py`：

1. 每次尝试创建唯一目录，写入该工况的 `spec.json`；
2. 使用工作站锁避免同时操纵同一 HYSYS 会话；
3. 启动 `python -m hysys_tools --spec ... --folder ...` 子进程；
4. 保存退出码、耗时、标准输出与错误输出；
5. 读取 `result.json` 并检查 `PASS`、案例文件、出口及校验证据；
6. 把结果记入台账，同一规格已成功的工况在恢复时跳过。

每个工况使用独立目录，是为了避免重复路径导致 HYSYS 返回旧的非空案例。若超时，适配器终止 Python 工作进程，不直接杀掉 HYSYS。缺失 `result.json` 会形成明确失败记录，不能被当作成功。

**代码定位**：[逐工况执行及状态门控，第 27–87 行](../reactor_agent/nodes/execute.py#L27)；[规格哈希和完成台账，第 63、120 行](../reactor_agent/adapters/run_store.py#L63)；[适配器写规格、启动进程并判定结果，第 306 行](../reactor_agent/adapters/hysys_cli.py#L306)；[工作站锁，第 211 行](../reactor_agent/adapters/hysys_cli.py#L211)；[缺失结果文件处理，第 401 行](../reactor_agent/adapters/hysys_cli.py#L401)。

## 10. 工具层：通过 COM 真正创建并求解案例

`hysys_tools/main.py` 收到规格后再次预检，再通过 HYSYS COM 执行：

```text
SimulationCases.Add 创建空白案例
→ 配置物性包和组分
→ 配置反应或 Gibbs 候选物种
→ 建进料、反应器、出口物流并连接
→ 设定温压及热边界
→ 求解并读回实际出口
→ 独立校验
→ 保存 .hsc、写 result.json/steps.json
→ 关闭本次创建的案例
```

工具层核对 `SimulationCases.Add` 返回的对象是否为本次可拥有的空白案例；保存和关闭也只针对这个对象，不通过 `ActiveDocument` 或可能重复的案例名操作。发生故障时尽可能保留失败案例与步骤记录，但不改动不属于本次运行的案例。

“读回”意味着不只检查 COM 属性有没有被设置，还检查 HYSYS 实际返回的组分、出口流量、温压、热负荷和求解器状态。Equilibrium 路线还会核对平衡常数配置，并利用出口实际组成计算 Q/K。

**代码定位**：[连接已运行的 HYSYS，第 589 行](../hysys_tools/main.py#L589)；[新建案例 `SimulationCases.Add`，第 119 行](../hysys_tools/main.py#L119)；[配置物性包与组分，第 236 行](../hysys_tools/reactor.py#L236)；[建物流、反应器并连接，第 676 行](../hysys_tools/reactor.py#L676)；[激活反应器、轮询求解器、读回出口，第 893 行](../hysys_tools/reactor.py#L893)；[保存并关闭本次案例，第 218–228 行](../hysys_tools/main.py#L218)。

## 11. 独立校验与报告

`hysys_tools/validate.py` 对读回结果进行校验，包括：

- 元素与质量守恒；
- Conversion 指定值与实际读回转化率；
- Equilibrium 各反应的 `Q/K`；
- 气化固体碳的去向与 CO 收率定义；
- 热负荷、求解器状态和必要的结果证据。

通过后，`reactor_agent/report.py` 生成中文解释。多个工况会显示并排对比和温度趋势；报告区分用户给定值、用户确认值、系统默认假设和 HYSYS 计算值。模拟数值来自工具层 `result.json`，而不是由大模型重写。

例如验收记录中，600°C 与 710°C 的重整甲烷转化率分别约为 **30.50%** 和 **54.16%**，外部供热约为 **20.24 MW** 和 **40.06 MW**。`Q/K` 接近 1 说明出口与本次使用的平衡常数自洽，但不能单独证明高温热力学数据的绝对准确性。

**代码定位**：[统一结果校验，第 714 行](../hysys_tools/validate.py#L714)；[元素与质量守恒，第 47 行](../hysys_tools/validate.py#L47)；[转化率检查，第 103 行](../hysys_tools/validate.py#L103)；[CO 收率，第 181 行](../hysys_tools/validate.py#L181)；[中文报告生成，第 132 行](../reactor_agent/report.py#L132)；[多工况对比，第 441 行](../reactor_agent/report.py#L441)；[结果写入 `result.json`，第 82 行](../hysys_tools/main.py#L82)。

## 12. 主要状态与产物

| 状态 | 含义 | 是否启动 HYSYS |
| --- | --- | --- |
| `WAITING_INPUT` | 有必须由用户确认的条件 | 否 |
| `UNSUPPORTED` | 工程选型或工具能力不允许执行 | 否 |
| `READY` | 规格已编译并通过预检 | 方案模式下否；执行模式下将进入执行节点 |
| `PASS` | 工况执行及证据检查通过 | 是 |
| `PARTIAL` / `FAILED` | 部分工况成功或执行失败 | 可能已执行部分工况，须查看记录 |
