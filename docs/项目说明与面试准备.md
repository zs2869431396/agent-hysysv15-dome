# AI 驱动的 HYSYS 化工反应器建模：项目说明与面试准备

> 依据当前仓库代码、`docs/tool-acceptance-20261003-105341.json` 和仓库内远程验收压缩包整理。本文把**已保存的工具层真机证据**、**开发文档的工作站反馈**和**离线测试**分开表述。面试时请按自己实际参与的工作调整“我负责”的说法。

## 一、先用一句话讲清项目

用户用自然语言描述反应体系和操作条件；大模型负责把原文抽成结构化事实；确定性程序负责选型、补充说明、预检和追问；通过后由 Python 通过 COM 驱动 Aspen HYSYS V15 建立并求解案例；程序读回模拟结果、做独立校验，最后生成中文报告和可追溯的运行文件。

最重要的边界是：**大模型不直接操作 HYSYS，也不直接编造最终计算值**。报告中的模拟数值来自 HYSYS 的结果文件；未执行时只能称为“模拟方案”。

## 二、为什么做、解决了什么问题

传统操作需要人工阅读题目、确定反应器、换算单位、配置物性与反应、逐个建模、摘录结果。自然语言输入容易存在缺失或歧义，例如“80000 Nm³/h”没有说明指哪股流量、标准状态是什么。这个项目把人工流程拆成可检查的阶段：抽取事实 → 判断能否建模 → 明确假设或提问 → 自动建模 → 检查结果 → 出具解释。它追求的是可复现的工程计算流程，不是让聊天模型“猜”一个答案。

适用范围是仓库中三个主要场景：甲苯歧化、甲烷蒸汽重整和简化的水煤浆气化。它不是通用化工设计平台，不能替代工艺设计审核。

## 三、架构和一次请求的完整数据流

```text
用户自然语言 / Streamlit 或 CLI
  → LLM 抽取字段（组分、流量、温压、反应、工况）
  → 程序做基础字段校验和原文溯源，标记无依据的值
  → review 节点：程序先补回原文明示的单位/组成基准，并试规划、预检以定位缺口
      ├─ 没有可补漏的目标字段：跳过第二次 LLM 调用
      └─ 有目标字段：LLM 仅核对这些字段并引用原文；程序验收修正、再次预检
  → plan 节点：归一化、反应器选型、能力检查、编译为严格 JSON 规格并最终预检
  → 有阻塞问题：LangGraph 暂停，用户确认后从检查点继续
  → 无阻塞且选择执行：适配器串行启动 hysys_tools 子进程
  → HYSYS COM 建案例、求解、读回、校验、保存 .hsc 和 result.json
  → 程序生成中文解释、工况对比和过程记录
```

| 模块 | 主要职责 | 关键文件 |
| --- | --- | --- |
| 界面与入口 | 中文聊天、方案/执行模式、追问、下载；CLI 用于运行和验收 | `reactor_agent/streamlit_app.py`、`reactor_agent/__main__.py` |
| 模型抽取 | 调兼容 Chat Completions 的模型服务；字段结构校验、原文 grounding | `llm.py`、`extraction.py` |
| 输入恢复 | 由程序先发现缺口，模型只针对白名单字段给带原文引用的候选补充 | `input_recovery.py`、`review.py` |
| 规划 | 单位与组分归一化、选型、能力检查、编译、预检 | `normalize.py`、`selection.py`、`capabilities.py`、`compiler.py` |
| 状态控制 | `intake → review → plan → ask/execute → explain`；SQLite 检查点 | `graph.py`、`nodes/` |
| 执行适配 | 每工况新目录、工作站互斥锁、超时、结果台账、失败证据 | `adapters/hysys_cli.py`、`adapters/run_store.py` |
| HYSYS 工具 | 严格规格预检、COM 建模和读回、独立校验 | `hysys_tools/precheck.py`、`main.py`、`reactor.py`、`validate.py` |
| 报告 | 展示输入、假设、选型理由、结果、校验与警告 | `reactor_agent/report.py` |

数据契约分层：`ProcessRequest` 保存用户事实，允许真实缺失；`ModelingPlan` 保存工程选型、假设、追问及多个工况；工具层使用 `hysys-agent/spec/1` JSON 规格。模型输出不能越过程序校验直接变成 COM 参数或文件路径。

**追问机制**：`plan` 收集阻塞问题；`ask` 用 LangGraph `interrupt` 暂停；回答可从 SQLite 检查点恢复并重新规划。气化的默认解释只有用户确认后才进入事实和规格。`execute` 是唯一实际启动模拟的图节点，只有 `READY` 且处于执行模式才运行。运行台账按规格识别已完成工况，避免恢复时重复求解。

**执行机制**：每个工况由适配器创建唯一目录和 `spec.json`，调用 `python -m hysys_tools`。工具层先离线预检，再通过 `SimulationCases.Add` 创建空白案例，配置物性、组分、反应、物流和反应器，求解后读回出口、保存 `.hsc`，写入 `result.json` 与步骤记录。成功判定综合子进程退出码、结果状态以及案例和出口/校验证据。超时终止 Python 工作进程，不直接杀掉 HYSYS。它只保存/关闭本次确认由自己创建的案例，避免误动操作人员的案例。

### 各模块传递什么字段：从用户事实到模拟结果

同一个工况会经过不同数据契约。不要把这些字段当成一张越来越大的表：`facts` 记录抽取结果，`ProcessRequest` 记录归一化后的用户需求，`ModelingPlan` 记录工程决策，`spec.json` 是工具输入，`result.json` 是工具输出。LangGraph 的 `AgentState` 把各阶段状态串起来。

| 层次 | 主要字段及含义 | 由谁产生、交给谁 |
| --- | --- | --- |
| 首次抽取 `facts` | 组分、组成、流量、温压、反应、动力学、转化率和工况；缺失字段保留为空 | `intake` 调模型抽取，交给 `review` 和 `plan` |
| 输入审核 `review` | 预检前后状态、目标字段、程序直接恢复的信息、模型候选修正与拒绝原因 | `review` 节点记录补漏过程，更新 `facts` |
| 归一化 `ProcessRequest` | 用户需求的规范化模型：进料、反应、工况、约束、相态和来源 | `normalize` 产生，供选型与规划使用 |
| 工程计划 `ModelingPlan` | 选型结论、能力状态、物性包、热边界、工况、假设、问题和状态 | `plan` 产生，交给编译器 |
| `spec.json` | 每个工况一份可执行建模规格：物性、进料、反应、反应器和假设 | 编译器产生，`hysys_tools` 读取 |
| `result.json` | HYSYS 求解与读回数据、独立检查、案例文件及错误证据 | `hysys_tools` 产生，适配器与报告模块读取 |

**1. 首次抽取字段（`facts`）。** [抽取契约](../reactor_agent/extraction.py#L103)包含以下 29 个顶层字段，按用途分组记比逐个背更容易：

| 类别 | 字段 | 用途 |
| --- | --- | --- |
| 物种与组成 | `species`、`feed_composition[{name, fraction}]`、`composition_basis` | 列出参与建模的组分、进料组成及摩尔/质量基准；`fraction` 可暂存原文中的比例或百分数，由程序归一化 |
| 反应与转化率 | `reactions[{name, species[{name, coefficient}], reversible}]`、`conversion_percent`、`conversion_basis` | 负计量系数代表反应物、正数代表产物；转化率是用户给定的约束，其基准组分另存 |
| 动力学与设备 | `rate_law`、`pre_exponential`、`activation_energy`、`activation_energy_unit`、`reaction_order[{name, order}]`、`reactor_volume`、`reactor_volume_unit`、`residence_time`、`residence_time_unit`、`catalyst_mass`、`catalyst_mass_unit` | 判断用户是否给出足够的速率方程和设备尺度；缺失时不能假装有动力学依据 |
| 进料与相态 | `phase`、`feed_total`、`feed_unit`、`feed_temperature`、`feed_temperature_unit`、`feed_pressure`、`feed_pressure_unit` | 记录进料相态、总流量和入口温压；数值与单位分开存，便于核对原文 |
| 分工况条件 | `case_pressures`、`case_pressure_unit`、`outlet_temperatures`、`outlet_temperature_unit` | 一个请求中多个压力或出口温度可拆成多个模拟工况 |
| 缺失记录 | `missing_information` | 模型报告原文没有提供的信息；程序仍会独立检查，不能只相信这份列表 |

例如用户写“甲苯 10000 kg/h，380°C，2.5 MPa，转化率 50%”，抽取层分别存 `feed_total=10000`、`feed_unit='kg/h'`、`feed_temperature=380`、`feed_temperature_unit='C'`、`feed_pressure=2.5`、`feed_pressure_unit='MPa'`、`conversion_percent=50`。这些值尚不是 HYSYS 输出。[原文溯源](../reactor_agent/extraction.py#L592)会把没有原文依据的字段名放进 `ungrounded`，阻止其直接进入模拟。

**2. 审核与流程状态字段。** [输入补漏记录](../reactor_agent/input_recovery.py#L114)中的 `original_facts` 保存首次抽取快照；`source_recoveries` 记录程序从原文明示信息补回的单位/组成基准；`target_fields` 是预检发现的可补漏目标；`precheck_before`、`precheck_after` 对比修正前后；`corrections`、`rejected_corrections`、`unchanged_corrections` 分别记录采纳、拒绝和未改变值的建议，`ignored_questions` 保留但不采纳模型自拟问题。[`AgentState`](../reactor_agent/nodes/state.py#L27)还携带 `text`、`facts`、`review`、`ungrounded`、用户 `answers`、待确认 `blocking/pending_questions`、`decision`、`cases`、执行 `executions`、`status`、`problems` 和最终 `explanation`。它是流程工作台，不等于发给 HYSYS 的全部参数。

**3. 归一化需求与工程计划字段。** [`ProcessRequest`](../reactor_agent/schemas.py#L236)含 `source_text`、`components`、`reactions`、`feeds`、`operating_cases`、`kinetic_data`、`conversion_constraints`、`field_sources`、`phase`、`has_solid_reactant` 等。[`FeedSpec`](../reactor_agent/schemas.py#L81)明确一股进料的 `basis`、`fractions/flows`、`total_flow` 与单位、温压；标准体积流量还需要 `flow_input='normal_volume'`、`standard_temperature_C` 和 `standard_pressure_kPa`。[`OperatingCaseRequest`](../reactor_agent/schemas.py#L221)保存每个工况的出口温度、压力及热边界。

[`SelectionDecision`](../reactor_agent/schemas.py#L310)区分工程上推荐的 `preferred_reactor` 和工具能运行的 `execution_reactor`，并记录 `rule_id`、`evidence`、`capability_status`、`explanation`。[`ModelingPlan`](../reactor_agent/schemas.py#L371)再把 `request`、`decision`、`components`、`property_package`、`thermal_mode`、`cases`、`assumptions`、`questions`、`status` 放在一起。`assumptions` 还记录取值来源，例如用户原话、用户回答、程序默认或推导，避免把假设说成用户输入。[`Question`](../reactor_agent/schemas.py#L268)用 `blocking` 区分必须先回答的问题与只需在报告里提示的问题。

**4. 工具输入 `spec.json`。** [编译器](../reactor_agent/compiler.py#L329)为**每个工况**生成一份 JSON：顶层有 `schema`、`case_name`、`scenario`、`fluid_package`、`feeds`、`reactions`、`reactor`、`assumptions`、`open_questions`。`fluid_package` 写物性包和组件；`feeds` 写物流名称、组成基准、组成/各组分流量、总流量与单位、入口温压；`reactions` 写计量系数，Conversion 才写给定转化率；`reactor` 写反应器 `kind`、`thermal_mode`、压降和必要时的出口温度。Gibbs 路线的 `reactions` 可以为空，因为它依据候选物种做自由能最小化。若仍有阻塞问题，[`compile_plan`](../reactor_agent/compiler.py#L411)保持 `WAITING_INPUT`，不产生可执行规格。

**5. 工具输出 `result.json`。** [工具层](../hysys_tools/main.py#L60)先写 `schema`、`tool_revision`、`status`、起止时间、`reactor_kind`、假设、警告与步骤；成功后补充 `case_file`、`outlet`、`component_flows_kmol_h`、`feed_molar_flows_kmol_h`、`heat_duty_kW`、`solver_evidence`、`checks` 等。[`outlet`](../reactor_agent/adapters/hysys_cli.py#L135)中的每股物流可读到温度、压力、摩尔/质量流量和摩尔组成；`checks` 包括对应场景的守恒、转化率或平衡校验。Equilibrium/固碳饱和路线会另带专属证据；失败时则可能出现 `error`、`error_type`、`traceback` 或失败案例路径。适配器读取这些字段并核对退出码与案例/出口/校验证据，报告模块再用它们生成中文解释。

## 四、反应器如何选

规则在 `selection.py`，顺序大致是：完整动力学及相态 → CSTR/PFR；已知转化率 → Conversion；可逆且有平衡信息或闭合反应网络 → Equilibrium；高温、多候选产物且难以用有限反应式封闭 → Gibbs；信息不足则追问或报告不支持。选择“工程上合适的反应器”与“工具是否实现”是两件事：若选出 PFR，当前工具层仍会报告 `unsupported`，不会暗中改成 Conversion。

能力表按模型、热边界、相态、反应数、是否含固体逐格判断：`verified` 表示当前工具层字节与真机验收哈希一致并有对应记录；`experimental` 表示存在代码路径但未完成真机验收；`unsupported` 不执行。`PengRob` 是规格默认物性包。具体物性模型是否足够适合某个工业体系，仍需工程复核。

## 五、三个场景要讲透

### 1. 甲苯歧化

- **给定条件**：纯甲苯 10000 kg/h、380°C、2.5 MPa、转化率 50%；总反应 `2 C7H8 → C6H6 + C8H10`。
- **选型**：已知转化率、没有动力学参数，采用单反应 Conversion。题目未给三种二甲苯分配和热边界，方案采用邻、间、对二甲苯等摩尔分配及绝热，报告需明确这两项是建模假设。
- **结果**：验收包中的绝热出口约 **378.28°C**；甲苯摩尔分数 **50%**、苯 **25%**、三种二甲苯各约 **8.33%**；读回甲苯转化率 **50%**，热负荷按绝热条件为 0。
- **核对**：元素和质量守恒、指定转化率与读回转化率一致、出口组成与化学计量及分配假设一致。
- **面试边界**：50% 是用户给定的约束，不是系统预测出的催化剂转化率；没有动力学和选择性数据，不能预测真实催化剂表现。

### 2. 甲烷蒸汽重整

- **给定条件**：`CH4 + H2O ⇌ CO + 3H2`，`CO + H2O ⇌ CO2 + H2`；甲烷:水蒸气 = 1:2.7；进料 520°C；13.5 bar；分别比较 600°C 和 710°C 出口。
- **选型**：两条反应覆盖已列组分，反应网络闭合；没有动力学和指定转化率，按等温气相 Equilibrium 建模，同时保留 Gibbs 对照。允许自定规模，所以选甲烷 **1000 kmol/h**、水 **2700 kmol/h**，这属于已声明的系统假设。
- **方法**：工具层从 HYSYS 组分 Gibbs 数据在目标温度附近拟合 `ln K`，写入 Equilibrium 反应并读回系数；出口用实际分压计算 `Q/K`，门槛是 `|ln(Q/K)| < 0.05`。这只是内部自洽性检查，不保证底层高温热力学数据的绝对准确性。
- **结果**：600°C 时甲烷转化率约 **30.50%**、外部供热 **20.24 MW**；710°C 时约 **54.16%**、**40.06 MW**。升温后重整更充分，但维持较高温度需要更多供热。这里的热负荷包含从入口加热到指定出口温度的显热及反应热，不等于单纯反应焓。

### 3. 简化的水煤浆气化

- **给定条件**：80000 Nm³/h、40 bar、水煤浆 62 wt%、进料 40°C、出口 1400°C、忽略灰分，求组成和 CO 收率。
- **先追问**：Nm³/h 指哪股流量、标准状态为何；煤是否可按纯固体碳表示。验收案例使用用户确认的默认解释：**单股混合总进料的标准体积当量，0°C / 101.325 kPa；煤按纯碳**。这不是未经确认就推断煤的真实组成。
- **选型与实现**：高温且副反应/候选产物多，选 Gibbs 路线。但 HYSYS 库中 Carbon 的 Gibbs 数据不适合直接用于此处固相碳；实际实现是 **Conversion 反应器 + 仅气相 Gibbs 反应器 + 外层迭代**，用固碳饱和条件求碳转化率。能力表把它称为 `gibbs + solid_carbon=saturation`，不能说成“单台 Gibbs 反应器直接处理煤”。
- **结果**：验收包中 CO 收率约 **40.14%**、碳转化率约 **41.16%**、湿基气相 CO 摩尔分数约 **50.01%**，外部供热约 **84.66 MW**；残余固体碳单独报告。HYSYS 返回的 `LIQUID` 出口在此路线中承载固相碳，不代表真的预测出液态碳。
- **指标口径**：`CO 收率 = (出口 CO 摩尔流量 − 入口 CO 摩尔流量) / 入口碳原子摩尔流量 × 100%`。它与碳转化率、CO 摩尔分数不同。由于题目无氧气进料，不能称为自热气化；维持 1400°C 的热量来自外部。

## 六、可靠性设计与项目难点

1. **防编造与缺口处理**：抽取值需能回到原文的数值、单位和物理量；候选补漏限于预检发现的字段，并附原文连续引用。无效回答不能解除阻塞，模型自己提出的问题不能直接成为系统追问。
2. **输入与执行隔离**：有阻塞问题时图停在 `ask`，没有 `.hsc` 案例；dry run 只生成方案。这个设计避免“先算了一半再追问”。
3. **仿真结果不能只看求解器是否停下**：读回组分和流量，检查元素/质量守恒、转化率、热边界、Equilibrium 的 Q/K、气化的固相去向和 CO 收率定义；失败写证据，不将结果包装成成功。
4. **COM 的状态与所有权**：新目录、新案例、串行执行、保存后关闭；拒绝非空或不属于本次运行的案例。这样避免重复路径和活动案例造成交叉污染。
5. **报告与证据**：同一渲染器供图流程与单遍流程使用；报告区分用户给定、系统默认和用户确认，结果旁保留校验、警告、原始 `result.json` 和 `.hsc`。

### 90 秒流程版

“我做的是一个用自然语言驱动 HYSYS 模拟的原型。用户在 Streamlit 页面或命令行里描述进料、反应和工况，系统首先让大模型把文字整理成结构化字段，比如组分、流量、温度和压力。

接下来不是马上运行 HYSYS。程序会核对这些字段有没有原文依据，并试着生成模拟方案，看是否漏了必需条件。如果只是模型漏抄了原文已经写明的信息，才让模型针对缺失字段回原文查找；模型给出的补充还要由程序核对。原文确实没说清的条件，则直接问用户。

信息齐全后，程序按规则选反应器，检查当前工具是否支持，再把每个工况编译为严格的 JSON 规格。用户选择执行且规格通过预检时，适配器启动独立的 Python 工具；工具通过 COM 操作 HYSYS 建案例、求解并读回数据。最后程序检查结果，保存 HYSYS 案例和 JSON，并生成中文报告。简单说，AI 负责理解文字，程序负责判断能否执行，HYSYS 负责真正计算。”

### 2—3 分钟完整流程版

“这个项目解决的问题是：用户能用自然语言描述化工反应体系，但 HYSYS 需要明确、可执行的建模参数。我的做法是把‘理解输入、审核输入、决定方案、执行模拟、解释结果’拆成一条可追溯的流程。

第一步是输入。用户在 Streamlit 页面或者 CLI 提交需求，同时选择只生成方案，还是实际执行 HYSYS。大模型先做一次字段抽取，把原话中的组分、流量、温压、反应和各个工况整理成结构化事实。它只负责提取，不能直接控制 HYSYS，也不能给出所谓的模拟结果。

第二步是检查。程序会验证字段格式，并核对抽取出的数值能否在原文中找到对应的数值和物理量。随后 review 节点先尝试用规则补回原文明示但漏抽的单位或组成基准，再用已有的规划规则试检一次，找出具体缺口。如果确有可补漏的目标字段，才第二次调用模型，让它只回原文查这些字段并附上原文证据；程序会逐条验收，不接受无依据的改动。如果原文本身没有给出关键条件，就由程序向用户追问，而不是让模型猜。

第三步是正式规划。plan 节点把字段归一化，按照工程规则选择反应器，再查项目的能力表。比如明确给定转化率时倾向 Conversion；有完整动力学时会按相态建议 CSTR 或 PFR，但这两类当前尚未实现，所以会说明无法执行。对可执行的工况，程序编译出严格的 JSON 规格并再次预检。有阻塞问题时，LangGraph 暂停，用户回答后从检查点继续规划；没有问题时状态变为 READY。

第四步才是工具调用。只有用户选了执行模式，execute 节点才把每个工况的规格交给适配器。适配器写出 spec.json，串行启动 hysys_tools 子进程。这个工具通过 Windows COM 连接正在运行的 HYSYS，创建新的案例，配置物性、组分、反应、物流和反应器，然后求解并读回出口数据。它把案例保存为 .hsc，把结果和操作步骤写成 JSON。

最后，主程序读取 result.json，检查工具状态、结果证据以及守恒、转化率或平衡关系，再生成中文报告和工况对比。以甲苯歧化为例，题目给了 50% 转化率，所以程序选 Conversion；这里的 50% 是用户提供的约束，真正的出口组成和温度要从 HYSYS 读回。整个项目的核心边界是：模型理解输入，程序控制流程和校验，HYSYS 产生计算数值。仓库中可复核的是工具层六工况真机验收，智能体层另有离线回归和工作站反馈。”

### 面试官追问“各模块字段怎么传”时的 60 秒回答

“我把数据分成五层，避免让模型输出直接变成 HYSYS 操作。第一层是 `facts`，只记录从用户原文抽到的组分、组成、流量、温压、反应和工况，缺失的值可以为空。第二层是流程状态，保存原文溯源失败的字段、补漏记录、用户回答和阻塞问题；比如模型给出的压力在原文中找不到，就标记为 `ungrounded`，不能直接执行。第三层是归一化需求和建模计划，记录选了什么反应器、为什么选、工具是否支持、有哪些假设及工况。第四层是每工况一份的 `spec.json`，它是给工具的操作单，明确写物性包、进料、反应器和热边界。第五层是 HYSYS 计算后生成的 `result.json`，包含出口组成、热负荷、案例文件和守恒或平衡检查。这样每层的职责清楚：用户输入和程序假设可区分，工具只接收经过预检的规格，报告只引用实际读回的结果。”

### 4—5 分钟完整讲述版

“这个项目的背景是，化工模拟不只是把题目交给 AI 让它写一个数值答案。真正的工作包括理解输入、确定合适的反应器、配置 HYSYS、求解、核对结果和解释假设。我的目标是把这条链路做成一个用户能交互、能追溯的流程。

系统分成智能体层和工具层。前端是 Streamlit 中文聊天界面，也提供 CLI。智能体层用大模型抽取事实，之后由 Python 进行归一化、选型和预检。输入不足时，LangGraph 会暂停并询问用户；答案确认后从检查点继续。执行模式才会调用工具层，方案模式只输出准备好的规格。工具层每个工况都新建一个目录和 HYSYS 案例，通过 COM 配置物性、反应器和物流，求解后读回结果，做独立校验并保存 `.hsc` 和 JSON 结果。

选型没有完全交给大模型。给了动力学且相态明确时，规则会建议 CSTR 或 PFR，但当前工具不支持执行；给了转化率时选 Conversion；可逆且反应网络闭合、没有动力学和转化率时选 Equilibrium；高温复杂体系则考虑 Gibbs。如果最合适的模型未实现，系统会如实标记不支持，不会悄悄换模型。

第一个例子是甲苯歧化。题目给纯甲苯每小时一万公斤、380 度、2.5 兆帕和 50% 转化率，所以用 Conversion。三种二甲苯没有给分配比例，系统说明采用等摩尔分配；热边界也采用绝热假设。验收中出口约 378.28 度，甲苯摩尔分数 50%、苯 25%、三个二甲苯各 8.33%。这里 50% 是输入约束，不是模型预测。

第二个例子是甲烷蒸汽重整。两条反应分别是蒸汽重整和水煤气变换，网络可以覆盖列出的组分。系统采用等温气相 Equilibrium，在 600 度和 710 度各建一个工况。平衡常数由 HYSYS 的 Gibbs 数据拟合，求解后用出口组成计算 Q/K 验证。验收结果是甲烷转化率从约 30.50% 升到 54.16%，供热从约 20.24 MW 升到 40.06 MW。Q/K 接近 1 代表模型内部自洽，不能证明高温热力学数据绝对准确。

第三个例子是水煤浆气化。它最关键的不是立刻计算，而是先确认题目中的 80000 Nm³/h 对应的进料和标准状态，以及煤能否简化为纯碳。确认后，系统用固碳饱和组合路线：先通过转化率反应器处理固碳，再让气相 Gibbs 反应器求平衡，并用外层迭代满足碳活度条件。验收结果中 CO 收率约 40.14%、碳转化率约 41.16%，这两个数与气相 CO 摩尔分数不是同一个指标。题目没有氧气，所以 84.66 MW 是外部供热，不能宣传为自热气化。

实现中比较有挑战的是防止模型漏字段或编造数值，以及控制 HYSYS COM 的状态。我们让程序先预检，有缺口才定向补漏；未确认的关键假设会阻塞执行。每次运行用唯一目录、工作站锁和结果台账，保存后只关闭自己创建的案例。求解成功仍要看守恒、Q/K 和结果文件证据。工具层六个工况有真机验收记录，智能体和页面主要依赖离线回归与工作站反馈。我会把项目定位为覆盖三个已验证题型的可追溯原型，后续若要泛化，需要扩展物性验证、动力学反应器和更多真实工况。”

## 九、面试高频问题与参考回答

### 项目与架构

1. **这个项目里 AI 的价值是什么？** 自然语言抽取和有依据的缺口恢复，降低手工录入成本；选型、预检、计算及校验仍由程序和 HYSYS承担。
2. **为什么不让大模型直接选反应器并写报告？** 选型要可重复、可解释，错误会直接影响模拟；规则能列出证据和能力边界。报告只能引用实际结果和声明过的假设。
3. **为什么用 LangGraph？** 气化存在真实追问，需要暂停、保存状态、跨进程恢复，同时保证恢复不重复调用模型或重复执行工况。流程节点与执行副作用分离。
4. **为什么用 Streamlit 而不是前后端分离？** 目标是同一 Windows 工作站上的本地演示，Python 界面可复用业务逻辑，部署成本低；多用户或远程生产环境需重新设计服务边界。
5. **为什么用 COM 而不是鼠标自动化？** COM 能直接创建和读取对象，路径和返回值可记录与测试；录制鼠标操作对窗口状态敏感，难证明模型配置和结果读回正确。
6. **JSON 规格有什么用？** 把自然语言层与 COM 工具层隔开，承载组件、物性包、进料、反应器、热边界和工况；可离线预检、保存、复现与审查。

### 化工与结果

7. **Conversion、Equilibrium、Gibbs 的区别？** Conversion 由给定转化率约束反应进度；Equilibrium 对指定反应按平衡常数求平衡；Gibbs 在候选物种集合内按自由能最小化求平衡，不要求列全反应式。三者仍依赖正确进料、组分和物性数据。
8. **为什么甲苯不选 PFR？** 题目未给速率方程、设备尺寸等动力学数据，却给了转化率；Conversion 适合这个受约束的模拟任务。它不能推导真实 PFR 尺寸。
9. **为什么重整选 Equilibrium 而不是 Gibbs？** 题目给出的 SMR 与 WGS 反应构成闭合网络，温度已指定，可对每个反应检查 Q/K；Gibbs 是有用的对照，验收两者结果接近。
10. **升温后重整结果为什么变化？** 蒸汽重整吸热，升温通常促进平衡向产物侧；实际结果中 CH4 转化率升高。水煤气变换是放热反应，升温对其平衡方向有相反影响。比较还应看 CO/CO2、H2 和热负荷，不只看转化率。
11. **为什么气化不能直接用库 Carbon 做 Gibbs？** 项目发现该库组分对应的 Gibbs 数据不适合直接代表这里的固相石墨；因此工具层拒绝普通单台 Gibbs 路线，使用固碳饱和外层求解。这个实现只验收了碳加水进料。
12. **CO 收率、碳转化率、CO 浓度有什么差别？** CO 收率按进料碳中净生成 CO 的比例；碳转化率按进料固碳中未留作固碳的比例；CO 浓度是某出口气体中 CO 的摩尔占比，分母不同。
13. **84.66 MW 是什么热量？** 为维持指定 1400°C 出口所需的外部热负荷，含升温显热和反应热；无氧气进料，因此不是自热气化的热平衡结论。
14. **Q/K 接近 1 能证明什么？** 在所用平衡常数、组成和压力口径下出口满足平衡条件，证明计算内部自洽；不能单独证明物性数据在高温区的绝对准确性。
15. **默认 PengRob 的风险？** 物性包影响相平衡、焓和热负荷；项目用已验收案例证明此实现能运行，工业设计仍需根据体系、温压范围及实验数据做物性方法适用性核查。

### 软件可靠性

16. **如何防止模型编造流量？** 将抽取字段与原文的数值、单位、物理量核对；缺乏依据的字段进入阻塞问题，用户有效确认前不能执行。补漏只能改预检发现的字段，不能清空已有事实。
17. **追问时会不会先创建部分案例？** 不会。图路由在 `plan` 后先进入 `ask`，执行节点只接受 `READY`；气化默认解释也要用户确认才生效。
18. **恢复运行怎样避免重复模拟？** SQLite 检查点保留流程状态，运行台账根据工况和规格记录已完成结果；同规格已完成工况跳过，变化的规格应当作为新执行处理。
19. **怎么判断模拟真的成功？** 同时看子进程退出码、工具层 `PASS`、案例文件及出口/检查证据，再检查守恒、转化率或 Q/K 等；缺 `result.json` 和超时都有明确失败记录。
20. **如何防止脚本改到用户正在看的案例？** 只使用 `SimulationCases.Add` 返回的新案例对象，核对它为空白且属本次运行；保存和关闭也只通过该对象，不用 `ActiveDocument` 或按不唯一的案例名关闭。
21. **模型服务不可用怎么办？** 记录分类错误并停止抽取，不生成伪结果。HTTP 重试、输出格式回退和请求次数有总预算，凭据在运行时提供。
22. **测试是如何分层的？** 纯逻辑与规格测试不依赖 HYSYS；假 COM/假模型响应测试故障路径；工作站真机验收验证六个工况及结果证据。离线测试不能替代真机。

### 复盘与开放问题

23. **最典型的 bug 是什么？** 重整的 `conversion_basis=null` 是合理缺失，却曾被 schema 当作错误，导致无效重试；修复为可空并加回归。另有甲苯二甲苯系数导致不守恒，以及气化已求解但报告层出错，分别靠配平预检与从保存结果恢复报告处理。
24. **最大的局限是什么？** 场景覆盖有限，CSTR/PFR 未实现；气化对煤纯碳和标况解释有强依赖；高温热力学数据的准确性没有外部实验验证；最新输入补漏分支仍需完整在线复核。
25. **如果继续做，会先做什么？** 先补完整聊天入口的工作站端到端证据及真实模型补漏回归，再扩展煤的元素分析、氧气/自热工况和物性数据验证；增加 CSTR/PFR 前需引入可信动力学参数与设备尺寸。
26. **如果面试官问“这是你独立写的吗”？** 如实说明自己完成的需求拆解、实现、调试、测试与验收工作，以及 AI 编程助手参与的部分。能现场解释关键代码、复现结果和边界，比笼统声称“全部独立”更有说服力。

### 字段与模块追问

27. **`facts`、`spec.json`、`result.json` 有什么区别？** `facts` 是从用户原文提取、尚可缺失的事实；`spec.json` 是程序归一化、选型和预检后生成的每工况建模指令；`result.json` 是 HYSYS 真实求解和读回的输出。不能把给定的转化率说成计算结果。
28. **为什么不把模型抽取的字段直接交给 HYSYS？** 原始字段可能漏单位、混淆物理量或包含无原文依据的数值；程序通过溯源、追问、选型和严格规格预检，才把它们编译为工具可执行的 `spec.json`。
29. **什么信息放在 LangGraph 状态里？** 原文、抽取事实、审核记录、无依据字段、用户回答、待确认问题、选型决定、各工况规格、执行结果和最终解释。检查点保存这些状态，回答追问后能继续同一任务；它不是直接传给 COM 的参数对象。
30. **`spec.json` 最重要的字段是什么？** `fluid_package` 决定物性和组分，`feeds` 决定进料，`reactions` 描述反应约束，`reactor` 决定设备及热边界，`assumptions` 说明用户未直接给出的建模选择。一个工况一份规格，便于复现和核查。
31. **结果里哪些是 HYSYS 算的，哪些是程序算的？** `outlet` 中的出口温压、流量、组成及热负荷来自 HYSYS 的求解与读回；程序基于进出口结果计算守恒误差、转化率或 Q/K 等检查，再生成文字报告。用户给定的参数和系统假设在规格中单独记录。
